## Cannot save

| Check | Fix |
|---|---|
| Rule shape | `NOT` needs one-element `children`; `VOTE.threshold` is a fraction, not a pass count |
| Expression type | Rules return booleans; sizing returns a number |
| Identifier policy | Use catalog-backed aliases; a name that looks plausible can still be rejected |
| Source/token metadata | Resolve decimals and action parameters rather than deleting unit checks |
| Execution plan | Review `execution_params.plan.steps`, hook effects, encoded arguments, chain, vault, and target family |
| Slippage budget | Set a positive budget on a budget-consuming step |
| Version | On `409 Conflict`, reload the current definition, compare changes, then submit a new reviewed update |
| Permissions | Inspect `canManage`/read-only mode and the supported session path; public reads do not confer write access |

Observed or source-tested diagnostics include:

| Diagnostic | Interpretation |
|---|---|
| `action_config: max_slippage_bps must be positive when the plan contains a budget-consuming step` | Missing/zero budget is not valid for that plan |
| `liquidity observations are not supported by simulation replay` | Simulation admission rejects the dependency; do not remove a production guard |
| HTTP 401 `{"error":"no_session"}` on public intent events | Detail/fills can be public while full events need a session |
| HTTP 409 on stale-version update | Someone changed the definition since your read |

Save validation is static. A division can pass save checks and still fail at runtime. See [Rules and expressions](/operate/strategy/dsl).

## Saved but not evaluating

Confirm the exact vault ID, strategy ID, version, and state. Only RUNNING strategies tick. A CREATED/IDLE definition is not broken because it has no intents.

For an intended RUNNING definition, inspect engine/shard availability, registered feeds, indicator warmup, referenced data availability, and the last evaluation time using authorized tools. Public strategy configuration alone cannot establish those values. Distinguish service errors from an access-denied telemetry request.

## Evaluating but no publication

Check in order:

1. Does the boolean rule pass on the actual raw snapshot, including exact boundaries and token identities?
2. Are referenced position, PPS, token-price, and exit-liquidity observations fresh and usable?
3. Does the size produce at least one raw unit after integer truncation?
4. Does current-tick conviction meet the required score?
5. Is the strategy in cooldown or holding an occupying intent slot?
6. Is the signal suppressed in its current epoch, or blocked by a risk limit, kill switch, breaker, or target emergency lock?

An empty Intent History does not prove the rule is false. The ledger is not every evaluation tick. Run a controlled evaluator fixture for expression behavior, then inspect production gates separately.

## Published intent without successful execution

Follow the exact intent ID through execution ID, events where authorized, fills, and transaction. Inspect:

- Hook/parameter authorization and active proof coverage.
- Source whitelist and oracle configuration.
- Session-key/executor readiness and execution gas, separately from upkeep.
- Available input balance, exit liquidity, quote freshness, and slippage budget.
- Venue constraints, transaction revert, expiration, or pending asynchronous settlement.

Do not retry blindly while an earlier intent can still settle. A terminal failure does not automatically bypass cooldown. Some async workflows release a slot before the entire lifecycle ends; count outstanding requests as well as active slots.

## Successful transaction, wrong resulting position

Check the first hook's denomination, amount propagated to each subsequent hook, source shares burned, assets received, debt reduction, interest, and residual balances. A liquidity cap may prevent the target even when execution succeeds.

The [AP1 historical trace](/operate/ui/intent-history) contains zero-address token placeholders and aggregate output zero, while its receipt records actual redemption proceeds. Neither a COMPLETED status nor that zero field is a complete economic interpretation.

For a high-LTV rule, recompute the post-action trigger. A move from 56% to 51% disarms the captured high-LTV and partial branches despite residual debt. [Deleverage and unwind](/operate/playbooks/deleverage) explains why this is not persistent recovery.

## Recovery record

Preserve the definition/version, observation timestamps, raw units, intent/execution/fill IDs, transaction hash, and exact error. State what remains unknown. Pause only the intended scope, reconcile in-flight work, fix the cause, and read back any approved configuration change before restarting.
