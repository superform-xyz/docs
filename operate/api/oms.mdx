The OMS implements the DeFiX intent execution path. The Strategy Engine publishes intents; OMS validates authorization, builds execution, submits hook transactions, and emits lifecycle events / fills back to operators.

**Browser prefix:** `/api/oms`. Paths below are upstream `/defix` contracts. OMS uses server-side service authentication, not a curator browser bearer-token recipe. The BFF checks the session and vault role; it supplies service credentials and actor attribution upstream. Direct service access requires explicit integration approval.

In normal dashboard operations, managers do not submit intents directly. They configure strategies and monitor the resulting intent history.

## Intent Lifecycle

OMS intent state is explicit and event-driven:

```text
RECEIVED → ACKED → STAGED → PLANNED → EXECUTING → COMPLETED
                                      ↘ ABORTED
                                      ↘ EXPIRED
                                      ↘ FAILED
                                      ↘ CANCELED
```

State values:

| State | Meaning |
|-------|---------|
| `RECEIVED` | OMS received the intent |
| `ACKED` | Intent accepted for processing |
| `STAGED` | Intent staged for planning/execution |
| `PLANNED` | Route or execution plan built |
| `EXECUTING` | Transaction execution in progress |
| `COMPLETED` | Execution completed |
| `ABORTED` | OMS aborted before success |
| `EXPIRED` | Intent expired before execution |
| `FAILED` | Execution failed |
| `CANCELED` | Intent cancelled before terminal execution |

Terminal states cannot be modified.

## Submit Intent

```bash
POST /defix/intents
```

This internal execution contract accepts a `SubmitIntentEnvelope`, not a Strategy create payload. The Strategy Engine constructs the intent from the current definition and execution plan. Do not copy a strategy JSON object directly to this endpoint.

Acceptance for processing is asynchronous, not a completed trade. Normal curator operation uses strategies and reads the resulting history rather than submitting raw OMS envelopes.

## Get Intent

```bash
GET /defix/intents/{intent_id}
```

Returns the current OMS state, latest sequence number, timestamps, and completion timestamp when available.

Fields such as `completed_at` may be `null` before terminal execution.

## Cancel Intent

```bash
POST /defix/intents/{intent_id}/cancel
```

Cancellation is asynchronous and subject to the current cancellable state. An accepted cancel request does not reverse a mined transaction or guarantee that an already submitted transaction will not settle. Read back intent state and reconcile receipts before retrying.

## Intent Events

```bash
GET /defix/intents/{intent_id}/events
```

Events are the source of truth for lifecycle reconstruction. Each event has:

- `event_id`
- `intent_id`
- `execution_id`
- `message_type`
- `seq_num`
- event-specific `payload`
- `created_at`

The Strategy Engine consumes these events and projects them into operator-friendly intent history.

## Fills and Mined Transactions

Fill records link recorded execution to transaction evidence. In the operator UI, fills may include:

- `tx_hash`
- `chain_id`
- `amount_in`
- `amount_out`
- `token_in`
- `token_out`
- `venue`
- `gas_used`
- mined / fill timestamp

Pre-receipt rows can have `null` gas or missing fill fields until the transaction is mined and backfilled. Placeholder token addresses, zero aggregate output, or a `COMPLETED` label are not economic reconciliation. Check receipt status, transfers, source shares, received assets, debt reduction, and residual balances. See [Intent History](/operate/ui/intent-history).

## Hook Transactions and Account Modes

OMS supports native hook transaction execution and smart-account/user-operation modes. Account mode controls how execution is signed and submitted:

| Mode | Meaning |
|------|---------|
| `OMS` | OMS-managed delegated signer path |
| `EIP4337` | ERC-4337 user operation path |
| `EIP4337_COMPANION` | Companion 4337 path |
| `EIP7702` | EIP-7702 account path |

The hook transaction adapter handles execution against SuperVault hooks once session-key and merkle authorization are valid.

## Session Keys

Strategy automation requires a valid session key for the vault.

### Readiness

```bash
GET /defix/vaults/{vault_id}/session-key/readiness
```

Returns executor manager membership, signing-configuration presence, session validity/expiry, pending rotation, and aggregate readiness. A ready session does not prove funded gas, valid hook proofs, or source liquidity. Infrastructure identifiers in authenticated responses are confidential.

### Grant

```bash
GET /defix/vaults/{vault_id}/session-key/grant
```

Returns calldata to grant a session key. The manager signs and submits the transaction.

### Rotate / Renew

```bash
GET /defix/vaults/{vault_id}/session-key/rotation
POST /defix/vaults/{vault_id}/session-key/rotation/complete
POST /defix/vaults/{vault_id}/session-key/rotation/cancel
```

Complete rotation after the grant/revoke transactions have mined.

### Revoke

```bash
GET /defix/vaults/{vault_id}/session-key/revoke
```

Returns calldata to revoke the current session key.

<Note>
Grant, revoke, and rotation preparation return transaction data for wallet signing. Readiness is a state read; rotation complete/cancel are service mutations. Even preparation GETs are manager-gated. Follow [Execution accounts and session keys](/operate/ui/execution-accounts), verify every required receipt, then refresh readiness.
</Note>
