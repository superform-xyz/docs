---
title: "Integrate SuperVaults"
description: "Let users deposit into and redeem from SuperVaults. Covers vault discovery via the Persephone API, deposit and redemption via the Bundler (one call → ordered transactions), and direct ERC-7540 contract interaction."
---

SuperVaults are ERC-7540 vaults on Base. An integration needs two things: **data** (vault metadata, APY, rewards, user positions) and **transactions** (deposit, redeem). Both paths are documented below with live-verified request and response shapes.

## Prerequisites

| Item | Value |
|---|---|
| Persephone API | `https://persephone.superform.xyz/v1` |
| Bundler API | `https://bundler.superform.xyz/` |
| Auth | No API key required for Persephone. Bundler requires `x-api-key` header — request a key at integrations@superform.xyz |
| Chain | Base (chain ID `8453`) |

---

## Step 1 — Discover Vaults

```bash
GET https://persephone.superform.xyz/v1/supervaults?chain_id=8453
```

No auth required. Returns all SuperVaults on Base.

**Key response fields per vault**

| Field | Type | Description |
|---|---|---|
| `id` | string | Stable vault ID: `{chain_id}_{address}` |
| `address` | string | Vault contract address |
| `name` | string | Onchain vault name (e.g. `NVDA SuperVault`) |
| `symbol` | string | Share token symbol (e.g. `superNVDA`) |
| `decimals` | number | Share token decimals |
| `availability` | string | `available`, `withdraw_only`, `paused` — always check before presenting deposit UI |
| `is_supervault_v_2` | boolean | Must be `true` — use `vault_type: "SUPERVAULT"` in bundler calls |
| `stats_basic.tvl_total` | number | TVL in USD |
| `stats_basic.reward_rate` | number | Current reward APR as a decimal (e.g. `0.1829` = 18.29%). For SuperStocks vaults, this is the yield figure to display — the underlying token tracks the stock price, so `apy_snapshot_week` is `0`. |
| `stats_basic.pps` | number | Price per share in underlying asset units |
| `stats_basic.pps_usd` | number | Price per share in USD |
| `assets[]` | array | Underlying asset(s): `address`, `symbol`, `decimals`, `price_usd` |

### Get a single vault

```bash
GET https://persephone.superform.xyz/v1/vaults/{id}
```

Same shape. `id` format is `{chain_id}_{vault_address}`.

### Historical APY and TVL

```bash
GET https://persephone.superform.xyz/v1/vaults/stats/historical/{ids}?start_ts=1727740800&end_ts=1728345600&granularity=day
```

`ids` is a comma-separated list. `granularity`: `hour` or `day`. Use for charting.

### User positions

```bash
GET https://persephone.superform.xyz/v1/balances/{address}
```

Returns all vault positions for a wallet: share balance, balance in USD, vault metadata.

## Step 2 — Deposit

There are two paths depending on your wallet type.

<CardGroup cols={2}>
  <Card title="Non-smart-account (EOA, Safe, Fireblocks, custodian)" icon="shield">
    One API call returns an ordered list of raw transactions to broadcast. No UserOps. The right path for most custodians and exchanges.
  </Card>
  <Card title="Smart account (ERC-4337)" icon="bolt">
    Three-call flow: suggest → build → execute. Used by the Superform app for embedded wallets.
  </Card>
</CardGroup>

<CodeGroup>

```bash Non-smart-account (custodians / EOA wallets)
# POST /hooks/suggest/non-smart-account
# Returns an ordered list of transactions to broadcast sequentially.
# Handles approval and deposit in one call.

POST https://bundler.superform.xyz/hooks/suggest/non-smart-account
x-api-key: YOUR_API_KEY
Content-Type: application/json

{
  "account": "0xUSER_WALLET_ADDRESS",
  "action": {
    "type": "DEPOSIT",
    "slippage": 50,
    "sources": [
      {
        "address": "0xb20000000000000000000078ee7ce2fe4908108c",
        "chain_id": 8453,
        "amount": "100000000"
      }
    ],
    "targets": [
      {
        "address": "0xc441a2cc3a528b6312740448a70cc4d40f4d7bfc",
        "chain_id": 8453,
        "vault_type": "SUPERVAULT",
        "amount_proportion": 1
      }
    ],
    "route_type": "OUTPUT",
    "outputs": []
  }
}
```

```bash Smart account (ERC-4337)
  "actions": [
    {
      "type": "DEPOSIT",
      "slippage": 50,
      "sources": [
        {
          "address": "0xb20000000000000000000078ee7ce2fe4908108c",

          "amount": "100000000"
        }
      ],
      "targets": [
        {
          "address": "0xc441a2cc3a528b6312740448a70cc4d40f4d7bfc",
          "chain_id": 8453,
          "vault_type": "SUPERVAULT",
          "amount_proportion": 1
        }
      ],
      "route_type": "OUTPUT",
      "outputs": []
    }

# Step 2 — Build UserOps from the suggest response
POST https://bundler.superform.xyz/executor/build
x-api-key: YOUR_API_KEY
Content-Type: application/json

{
  "account": "0xUSER_SMART_ACCOUNT_ADDRESS",
  "hooks": [ /* hooks[] from suggest response */ ],
  "fee_tokens_to_use": [ /* from suggest response */ ],
  "token_balance_changes": [ /* from suggest response */ ],
  "signer_type": "EIP4337"

# Step 3 — Sign the merkle_root, then execute
# signature = wallet.signMessage(build_response.merkle_root)

POST https://bundler.superform.xyz/executor/execute
x-api-key: YOUR_API_KEY
Content-Type: application/json

{
  "expiry": 1234567890,
  "merkle_root": "0x...",
  "user_ops": [ /* from build response */ ],
  "valid_after": "0",
  "fees_tokens": [ /* from build response */ ],

# Returns status: "PENDING" | "CONFIRMED" | "FAILED"
```

```solidity Direct contract (ERC-7540)
// For wallets that prefer direct contract interaction.
// Two transactions required: approve then deposit.

// Step 1: Approve the vault to spend the underlying asset
IERC20(0xb20000000000000000000078ee7ce2fe4908108c)
    .approve(
        0xc441a2cc3a528b6312740448a70cc4d40f4d7bfc, // NVDA SuperVault
        100000000 // amount in NVDAc (8 decimals)
    );

// Step 2: Deposit
// deposit(uint256 assets, address receiver) returns uint256 shares
uint256 shares = ISuperVault(0xc441a2cc3a528b6312740448a70cc4d40f4d7bfc)
    .deposit(100000000, receiverAddress);
```

</CodeGroup>

**Non-smart-account deposit response (live-verified)**

The bundler returns `executions[]` — an ordered list of transactions. Broadcast each one and wait for confirmation before sending the next.

```json
{
  "executions": [
    {
      "type": "DEPOSIT",
      "to": "0x833589fcd6edb6e08f4c7c32d4f71b54bda02913",
      "value": "0",
      "call_data": "0x095ea7b3..."
    },
    {
      "type": "DEPOSIT",
      "to": "0x11820afe50ea96851ee2bdbae329d97771e41ec6",
      "value": "0",
      "call_data": "0x6e553f65..."
    }
  ]
}
```

Execution 1 (`0x095ea7b3` selector) is `ERC20.approve(vault, amount)`. Execution 2 (`0x6e553f65`) is `ERC4626.deposit(assets, receiver)`. Both are labeled `type: "DEPOSIT"` — use array position to determine order.

**Request parameters**

| Field | Required | Description |
|---|---|---|
| `account` | ✅ | Wallet address that holds the source token and will broadcast |
| `action.type` | ✅ | `DEPOSIT` |
| `action.slippage` | ✅ | Slippage in basis points (`50` = 0.5%) |
| `sources[].address` | ✅ | Underlying token contract address |
| `sources[].chain_id` | ✅ | `8453` for Base |
| `sources[].amount` | ✅* | Raw token amount in smallest unit. Use `amount_fiat` for USD-denominated amounts |
| `targets[].address` | ✅ | SuperVault contract address |
| `targets[].vault_type` | ✅ | Always `"SUPERVAULT"` when `is_supervault_v_2: true` |
| `targets[].amount_proportion` | ✅ | `1` to route 100% of source into this vault |

> **Balance validation**: the bundler validates on-chain balance before returning calldata. The `account` address must hold at least the requested `amount`. Integrations should check balance client-side first to surface a clear error before hitting the API.

## Step 3 — Redemption

SuperVaults use **ERC-7540 async redemptions**:

1. **Request** — user submits shares → queued in escrow
2. **Fulfillment** — Superform's keeper fills the request (~1 hour)
3. **Claim** — user withdraws the fulfilled assets

<CodeGroup>

```bash Non-smart-account redemption
# Step A: Request redemption
POST https://bundler.superform.xyz/hooks/suggest/non-smart-account
x-api-key: YOUR_API_KEY
Content-Type: application/json

{
  "account": "0xUSER_WALLET_ADDRESS",
  "action": {
    "type": "REDEEM",
    "slippage": 50,
    "sources": [],
    "targets": [
      {
        "address": "0xc441a2cc3a528b6312740448a70cc4d40f4d7bfc",
        "chain_id": 8453,
        "vault_type": "SUPERVAULT",
        "amount": "100000000"
      }
    ],
    "outputs": [
      {
        "address": "0xb20000000000000000000078ee7ce2fe4908108c",
        "chain_id": 8453,
        "amount_proportion": 1
      }
    ],
    "route_type": "OUTPUT"
  }
}
# Broadcast the returned executions[] in order.
# Then poll maxWithdraw(account) on the vault contract until it is > 0.

POST https://bundler.superform.xyz/hooks/suggest/non-smart-account

    "slippage": 50,
    "sources": [],

      {
        "address": "0xc441a2cc3a528b6312740448a70cc4d40f4d7bfc",
```

```solidity Direct contract (ERC-7540)
interface ISuperVault {
    // Step A: Queue redemption — moves shares to escrow
    function requestRedeem(
        uint256 shares,
        address controller,
        address owner
    ) external returns (uint256 requestId);

    // Poll: claimable assets (0 until keeper fulfills)
    function maxWithdraw(address controller) external view returns (uint256);

    // Poll: pending shares (> 0 while unfulfilled)
    function pendingRedeemRequest(address controller) external view returns (uint256);

    // Step B: Claim after fulfillment
    function withdraw(
        uint256 assets,
        address receiver,
        address controller
    ) external returns (uint256 shares);
}

// Usage:
// 1. requestRedeem(shares, msg.sender, msg.sender)
// 2. Poll maxWithdraw(msg.sender) — proceed when > 0
// 3. withdraw(maxWithdraw(msg.sender), receiver, msg.sender)
```

</CodeGroup>

**Redemption state machine**

| State | How to detect | Next action |
|---|---|---|
| Pending | `pendingRedeemRequest(account) > 0` | Wait for keeper (~1 hour) |
| Fulfilled | `maxWithdraw(account) > 0` | Send `REDEEM_CLAIM` or call `withdraw()` |
| Claimed | `maxWithdraw(account) == 0` | Done |

## Key Concepts

**Price per share (PPS).** `stats_basic.pps` is the exchange rate between one share and the underlying asset. PPS only increases. Display a user's current value as `assetValue = shares × pps`.

**Reward rate vs APY.** For SuperStocks vaults (`superNVDA`, `superTSLA`, etc.), display `stats_basic.reward_rate` — this is the USDC reward yield. The `apy_snapshot_*` fields track price appreciation of the underlying token (NVDAc tracks NVIDIA stock), not a yield rate, and will often read `0` in flat markets. Use `reward_rate` for the APY figure.

**availability.** Always check before rendering deposit or redeem UI: `available`, `withdraw_only`, `deposit_only`, `paused`, `unavailable`.

**Balance validation.** The bundler validates source token balance on-chain before returning calldata. Check balance client-side first to show a clear error without an API round-trip.

**Slippage.** Pass in basis points. `50` = 0.5% (suitable for bStock vaults with RFQ liquidity). `10` = 0.1% (stablecoin vaults).

**Which endpoint to use.** `POST /hooks/suggest/non-smart-account` is for custodians, Fireblocks, Safe, and any wallet that broadcasts raw EVM transactions. The `/hooks/suggest` → `/executor/build` → `/executor/execute` flow is for ERC-4337 smart accounts with embedded signers.
