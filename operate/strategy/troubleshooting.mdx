## Cannot create or save

| Symptom | Check and action |
|---|---|
| No manager controls | Use the authenticated Operate surface with the required vault role; a public canvas is read-only |
| Unknown identifier or type error | Choose a supported variable and keep boolean rules separate from numeric sizing |
| Missing hook parameter or unknown size unit | Resolve the source, token decimals, hook, and required parameters before saving |
| Invalid plan | Review the generated `execution_params.plan.steps`, not a legacy single-hook body |
| `409 Conflict` | Reload and compare the latest version; reconcile changes before saving again |

Backend save validation checks shape and types. It does not execute the rule against an empty snapshot or prove the action can settle. Division by zero can still occur at runtime; guard the denominator first.

## No intent appears

Check these in order:

1. **Lifecycle:** is the intended strategy `RUNNING`, not just saved? Do not start an inactive exercise merely to investigate.
2. **Vault and target:** check kill switch, pause, emergency locks, upkeep, and execution readiness. Do not clear an incident lock to force a test.
3. **Inputs and rule:** inspect the current supported fields and their freshness. For the reserve example, idle exactly at the 10% trigger should not publish.
4. **Size:** check the first hook's units and positive integer amount. A sub-unit positive value truncates to zero.
5. **Publication gates:** check conviction, cooldown, rate limits, and an occupied per-strategy concurrency slot.

Intent History records submitted intents, not every false rule evaluation. If no row exists, use the editor's available state or authorized engine diagnostics; missing observations are not proof of a zero balance.

## An intent failed or is still executing

Open the exact intent and inspect state, error, execution ID, and fills before considering another submission.

| Evidence | Decision |
|---|---|
| `RECEIVED` through `EXECUTING` | Check timestamps and in-flight work; do not create a duplicate to get a faster result |
| Pricing timeout | Check service/feed recovery and whether another attempt is already active; keep price protections |
| Slippage or liquidity rejection | Review the quote, configured budget, and source capacity; do not automatically loosen limits |
| Hook transaction reverted | Inspect the transaction and authorization/proof path |
| `COMPLETED` but balance is unexpected | Match the fill to the receipt and check token/share units before inferring the result |

The [public deposit investigation](/operate/ui/intent-history#inspect-a-failed-deposit) includes a real pricing-timeout row and its empty fills response.

## Simulation does not answer the question

Check selected saved IDs, model inputs, and whether a result was loaded from cache. Unsupported inputs are a coverage limit, not a reason to remove a live safety condition. Follow the [run and review flow](/operate/ui/simulation#run-and-review).

For persistent failures, retain the exact ID/version, input context, error, and transaction evidence. Stop new risk-taking activity where appropriate and escalate. Archiving and cloning a failing strategy loses continuity and does not resolve the cause.
