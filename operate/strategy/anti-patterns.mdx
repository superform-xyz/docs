---
title: "Strategy anti-patterns"
description: "Avoid definitions that compile but misstate units, policy, execution, or recovery."
---

| Anti-pattern | Why it fails | Better design |
|---|---|---|
| Deposit every idle asset while claiming a reserve target | Sizing contradicts the stated objective | Deposit only excess above the target |
| Treat `vault_tvl` as USD or `vault_free_assets` as USDC in every vault | Engine accounting uses the vault underlying | Match the token and raw scale explicitly |
| Treat every `size_expr` as assets | Redeem hooks can consume shares | Inspect first-step effects and convert with actual decimals/PPS |
| Reuse first-hook share count for repayment | Repayment consumes debt tokens | Chain actual redemption output with `use_prev_hook_amount` |
| Assume save validation dry-runs zero inputs | Validation is static | Test zero/missing snapshots with the evaluator |
| Guard division in a different strategy or unsafe VOTE child | No cross-strategy short-circuit; vote/conviction can evaluate children independently | Keep denominator guards in the evaluated expression path |
| Set VOTE threshold to a count | The backend expects a fraction in `(0, 1]` | Use the desired passing fraction and test the rounded requirement |
| Treat conviction as consecutive passing ticks | Modes score the current evaluation | Use verified temporal indicators/policy if persistence is needed |
| Copy a dynamic alias and assume data exists | Shape validation does not prove feed availability | Inspect field, scale, provider, freshness, and readiness |
| Remove exit-liquidity guards to make replay run | Simulation coverage is narrower than production dependencies | Preserve the guard and report unsupported replay |
| Treat `max_concurrent: 1` as a portfolio lock | It applies to one strategy | Review shared-balance competition and vault-level controls |
| Treat card order as an atomic workflow | Priority is not a transaction dependency scheduler | Use a supported execution plan for dependent hooks |
| Call a liquidity-capped repayment a guaranteed target | Available resources can be insufficient | Measure the resulting debt and LTV |
| Call a high-LTV rule a persistent full unwind | Once the threshold is false, it stops | Track residual debt and the approved exit objective explicitly |
| Call pause an unwind | Pausing does not repay, redeem, or release collateral | Separate control scope from economic recovery |
| Treat COMPLETED or aggregate output as a reconciled outcome | Projection fields can be incomplete | Decode receipts and compare positions |
| Default missing service telemetry to success | Unknown becomes falsely healthy | Emit an explicit unknown condition |
| Retry a stale-version update unchanged | It overwrites or conflicts with newer intent | Reload, compare, and submit a reviewed update |

## A counterexample worth testing

A stateless rule triggers at 55% LTV and requests full repayment capped by available liquidity. If a partial fill moves LTV from 56% to 51%, the rule stops while debt remains. Neither the phrase “full unwind” nor a one-intent concurrency setting changes that behavior.

The [deleverage playbook](/operate/playbooks/deleverage) tests this case. The [reserve playbook](/operate/playbooks/reserves) tests resulting-state invariants rather than only whether a rule passes. Use [Troubleshooting](/operate/strategy/troubleshooting) to identify the failing stage before modifying production policy.
